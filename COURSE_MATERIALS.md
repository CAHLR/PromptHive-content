# Course Materials for Oski

The existing `/#/course-materials` UI, API, SQLite jobs, external worker, authentication,
upload verification and bounded review remain. The document-processing pipeline is
now bundled in **`abscribe_backend/course_materials_pipeline`**. The application no
longer needs or reads an OATutor checkout. `OATUTOR_REPO_PATH` is obsolete and ignored.
Google Sheets, hints, difficulty and Mongo-backed Editable Documents stay separate.

## What moved

Copied OATutor's BDA client, semantic compiler, OpenAI/Bedrock providers, compiler/
validator/embedding commands, schemas, publication/preflight/coordinator helpers,
and document-context/document-ID helpers required by embeddings. These are complete
local implementations, not wrappers importing another repo. The package has its own
Node 22 declaration, dependency manifest/lockfile and tests. Extraction, semantic
compiler, providers and runtime embedding helpers retain their original bytes;
UPSTREAM.json records source hashes for future comparison. OATutor's original files
were not changed. Credentials, node_modules, source PDFs and private archives were
not copied into Git. Local dependencies are installed with npm, not copied.

Only storage/code paths and necessary publication baseline handling changed. The
existing worker passes the bundled package path, managed data path and existing job
workspace to the adapters. Commands use argument arrays, no shell interpolation.
Their working directory is the bundled package; writable output is separate.

## Workflow and paths

Upload → verification/automatic queue → existing BDA extraction/compiler → existing
validation → bounded review → approval → additive lesson bindings → existing CLI
publication → verified Published. Upload may succeed while queueing is unavailable;
Process retries queueing without another transfer. Jobs survive browser navigation.

Writable data defaults to `abscribe_backend/instance/course-materials`, retaining
the existing SQLite, instructor accounts, uploaded PDFs, reviews and job logs.
Its `pipeline/` directory contains:

- `documents/raw/ph-<UUID>.pdf`: verified PDF, derived from server ID, not filename.
- `documents/compiled/ph-<UUID>.json`, namespaced `documents/assets/`, optional
  `.embeddings.json` sidecars and BDA cache. JSON is generated by the compiler;
  the original PDF never goes into compiled/.
- `documents/manifest.json` and `coursePlans.json`: working copies of the current
  runtime S3 configuration, not a hardcoded/second course catalog.
- `publication-state/`: existing lock, registration marker, baseline/ledger and
  CLI publication journal, now on ordinary durable disk rather than in Git.

`COURSE_MATERIALS_DATA_DIR` selects the existing durable store;
`COURSE_MATERIALS_PIPELINE_DATA_DIR` optionally selects a separate absolute working
storage directory. Both API and worker must use identical configuration and Node PATH.
The code package is not a place for mutable PDFs, configuration or secrets.

Compilation temporarily registers this ID under the shared lock and runs:

```sh
npm run compile-docs -- --doc ph-<UUID>
npm run validate-docs -- --doc ph-<UUID>
```

It stages successful artifacts in the existing private job workspace for review,
removes only its temporary manifest entry, and isolates incomplete output on failure.
The source PDF/logs remain for retry. Approval remains tied to exact content/assets,
metadata and assignments. Publication rechecks permissions, validation and hashes,
restores approved artifacts into managed working storage, merges the manifest and
adds bindings, then runs **`npm run publish-docs`**. Duplicate lesson variants receive
the union of existing IDs plus the new ID; ambiguous cross-course IDs are rejected.
Office Hours continues to use the course's lesson document union. No assignment
service, runtime format change or Lambda redeployment was introduced.

## Runtime configuration baseline

The existing worker runs the bundled `sync-config` command at startup and every
60 seconds while idle. It performs **read-only S3 GETs** for the existing
`<prefix>/manifest.json` and `<prefix>/coursePlans.json`, retaining exact bytes in
working storage. The API reads those local copies; request handlers do not block on
cloud calls. Missing configuration produces an actionable initialization error.

Sync validates formats and refuses to overwrite unpublished local edits, a changed
runtime target or a pending compilation/publication journal. Clean working copies
may refresh to newer runtime configuration; old approval hashes then become stale.
Publishing rechecks the runtime ledger and uses conditional writes, so stale local
configuration cannot silently overwrite a newer remote writer.

Existing baseline materials remain in S3. Publication retains their unchanged
manifest entries/bindings and checks missing-local compiled documents for remote
existence/identity. Newly compiled local materials receive full existing schema/
relationship/asset validation. Unrelated S3 artifacts are neither deleted nor
re-uploaded merely because they are absent locally. Local approved artifacts use
exactly the existing `<prefix>/compiled/...` and `<prefix>/assets/...` layout. The
publisher uploads content first, shared manifest next, coursePlans last, and marks
Published only after verifying local artifacts and both configuration hashes.

This necessary storage adaptation removes the old requirement to mirror an entire
OATutor checkout's documents. It does not introduce another publisher: the copied
CLI and existing coordinator still perform publication. Do not use an independent
stale OATutor publisher against the same S3 configuration; external changes are
protected by hash/ETag conflict checks, not a lock shared across separate hosts.

## Environment and startup

Both API and worker explicitly load backend **`.env.course-materials`** with
python-dotenv; `COURSE_MATERIALS_ENV_FILE` overrides its location. Existing process
variables take precedence. No code loads an OATutor `.env`, shell file or credentials
from another checkout. The shared server environment and standard AWS credential
chain remain; no credentials are embedded in code or frontend bundles.

Use Node **22.x** on API/worker/frontend PATH. Install once:

```sh
cd abscribe_backend/course_materials_pipeline
nvm use 22
npm ci
cd ..
poetry run pip install -r requirements-course-materials.txt
```

Use `.env.course-materials.example` for configuration. Existing variables are retained:

- Local upload/access: `COURSE_MATERIALS_LOCAL_DEV=1`, `COURSE_MATERIALS_UPLOAD_MODE=local`.
  Loopback only; no upload bucket/CORS change is needed. Optional direct S3 upload
  still uses UPLOAD_BUCKET/REGION, boto3 and exact-origin POST CORS; verified bytes
  are downloaded to raw/ before compilation.
- Extraction: `COURSE_MATERIALS_PROCESSING_ENABLED=1`, `COURSE_DOCS_S3_BUCKET`, BDA profile/account/project
  settings, `COURSE_MATERIALS_COMPILE_REGION` (default us-west-2), existing AWS identity.
- Semantic provider: `SEMANTIC_COMPILER_PROVIDER`, server-only `OPENAI_API_KEY`,
  optional `OPENAI_COMPILER_MODEL`/MAX_TOKENS or existing Bedrock model settings.
  Optional embeddings retain EMBEDDING_MODEL/DIMENSIONS. The worker prevents dry-run
  output from masquerading as real processing.
- Runtime sync/publication: `COURSE_DOCS_RUNTIME_BUCKET`, REGION (default us-west-1),
  PREFIX (default documents). `COURSE_MATERIALS_PUBLISH_ENABLED=1` enables explicit publication jobs.
- Private writable durable data directory, Node/npm and bundled dependencies.
  Neither OATUTOR_REPO_PATH, Git identity nor a content submodule is required.

Start from **abscribe_backend** (the repo root's email.py can shadow Python's standard
library), using the same environment for both processes:

```sh
poetry run python -m abscribe_backend.course_materials_api
# Separate terminal:
poetry run python -m abscribe_backend.services.course_materials_worker
# Frontend terminal:
cd ../frontend
nvm use 22
npm start -- --host 127.0.0.1 --port 5174 --strictPort
```

Open http://127.0.0.1:5174/#/course-materials. The same-origin feature proxy still
forwards to port 8082; existing authoring API settings remain separate. Supervise
one worker with a service manager and persistent local volumes. Long jobs renew
SQLite leases and have a one-hour timeout. Claims and shared configuration mutations
are serialized; no lock is held during instructor review. Readiness reports missing
bundled dependencies/configuration, storage, worker availability and disabled switches
separately. Configuration presence does not prove BDA/model/S3 write permissions.

The current private environment retains AWS profile `oatutor-docs`, staging bucket
`oatutor-course-docs-bucket` in us-west-2, existing BDA project/profile, and runtime
bucket `oatutor-runtime-course-docs` in us-west-1 with prefix `documents`. Credentials
were not printed/committed. Processing/publication switches remain OFF pending an
approved concrete live test. Read-only initialization fetched 22 courses and 154
manifest entries into PromptHive-managed storage without changing AWS resources.

## Authentication, review and recovery retained

Provisioned instructor accounts, course scopes, signed host-only Secure/HttpOnly/Lax
sessions, exact-Origin/custom-header CSRF checks and loopback restrictions remain.
Hosting still uses the documented same-origin Netlify proxy and a configured real
HTTPS backend; public hosting was not deployed/verified by this relocation.
Review still uses worker-prepared immutable indexes, versioned cursors, at most 12
fragments of 1,500 characters per page, paginated notes and lazy advanced JSON.
Individual assets verify only their membership/containment/hash; approval/publication
verify the complete artifact set. No fake cloud result is produced by the UI.

Before relocation, the designated OATutor checkout had no publication-state directory,
and all three existing durable material records were `uploaded`. No pending or
possibly active publication was discarded, and all original files remain intact.
New pending state lives in `pipeline/publication-state/cli-publication.json` and is
reused on retry. An interrupted registration blocks other writes until its own job
is retried. After activation is attempted, an error remains Verification pending;
assignments/approval stay frozen and Reconcile publication retries the original
operation. No automatic rollback or journal deletion is performed.

Manual CLI writers on this host must use the bundled entrypoints and the same data
directory. To inspect a pending publication, with the same environment:

```sh
# abscribe_backend/course_materials_pipeline
node scripts/publication-recovery.mjs --document-id cli
```

This only reads S3 and reports base/target/conflicts and artifact verification.
Resolve conflicting local/remote changes explicitly, preserve the original target
and last working runtime configuration, then reconcile. Back up the entire materials
data directory, SQLite/accounts, sources, job workspaces/logs, working configuration,
compiled/assets and publication state together. No Git commit, registry or private
Git archive is needed for new jobs. A code clone alone cannot restore private data.
Historical instructions in COURSE_MATERIALS_LEGACY_RECOVERY.md describe the prior
checkout-based implementation only; do not apply its Git paths to the new worker.
If a different installation has unresolved old Git journals, stop and migrate that
specific state explicitly rather than initializing over it. This installation had none.

### Focused recovery fixes

Configuration sync now records a small local `publication-state/config-sync.json`
intent before updating manifest, coursePlans, baseline and ledger. A retry verifies
all four files against their saved before/target hashes, then finishes only missing
writes and clears the intent. It can finish without S3 access; a later normal sync
checks for newer remote configuration. Genuine conflicting edits or a changed
runtime target preserve the intent and fail closed. Other pipeline operations wait
for the pending sync. Retry the existing `sync-config` command, or let the worker's
normal idle sync retry it; do not delete the intent to bypass a conflict.
Older unmarked partial syncs are accepted only where working bytes match the saved
ledger or current S3 bytes; unrecognized edits still require reconciliation.

Compilation verifies the uploaded PDF and existing working source before creating
new registration markers. Registration and file preparation are inside cleanup;
failures that have not registered a document release their unused markers without
rewriting the manifest. An older interrupted registration remains protected when
its source recheck fails, and failed artifact isolation retains recovery ownership.

Recovery verification: 47 pipeline tests, 63 backend materials tests, 43 frontend
tests and a Node 22 production build passed. The build was written to
`/private/tmp/cm-recovery-fixes-build`, preserving the existing frontend build.
Tests inject interruptions after every sync write (bootstrap and refresh), edits
to all four tracked files, and early compilation/source/setup failures. No paid
processing or live publication was performed. Publication performance and review
presentation are unchanged and remain follow-up work after the isolated live test.

### Library controls and cancellation

The page opens with a simple materials list, search and a status filter;
Upload material opens the existing form in a focused dialog. Review actions are
consolidated, and service diagnostics appear only when attention is needed. Mobile controls wrap and
material actions remain visible.

Cancel stops an unstarted upload/queued ingestion immediately. During ingestion it
records a durable request; the copied CLI checks before extraction, after BDA and
after semantic compilation. An in-flight cloud request may finish and incur charges;
later stages stop. The orchestration cleanup retains sources, isolates incomplete
output and removes temporary registration. The worker marks Cancelled only after
cleanup; cancelled records can restart. Publishing/recovery operations cannot be
cancelled or deleted while activation is unresolved.

Delete is **library removal**, not unpublishing or permanent file/S3 deletion.
Undo and the Deleted view were removed from the instructor UI to keep it simple.
Private sources, artifacts and receipts remain on disk for operator recovery. Published
materials continue to be available to Oski; the confirmation says so explicitly.
Shared manifest, lesson bindings and runtime S3 are never changed by deletion.
Cancel/delete/restore use the existing authentication, course scopes and origin
protection. Interrupted compilation registration must be recovered before deletion.

Local checks cover cancel/claim races, restart markers, active-worker cancellation,
publication recovery protection, recoverable deletion, course permissions and
pipeline cleanup. A clearly marked, never-queued TEST record verified cancellation,
delete, undo and restore after refresh in the browser; it was then removed and all
four original records/configuration verified unchanged. No paid processing or
publication was run for this UI update.

Verification for this UI/control update: **80 backend tests, 49 pipeline tests,

mobile 390 px were inspected in the browser with no document-width overflow.
Screenshots and test-only cleanup evidence are in `/private/tmp/cm-ui-redesign/`.

The simplified instructor page removes breadcrumbs, introductory copy, summary

### Creating a course during upload

In loopback development mode or an authenticated administrator session, the Course
selector includes **＋ Create new course…**. Enter a unique course name and 1–50
unique lesson names (one per line). The API generates stable lesson IDs and assigns
the uploaded material to all of these lessons. Course-scoped instructor accounts
cannot create courses or expand their permissions through this form.

The pending course lives only in the durable material record, not in the catalog or
shared coursePlans.json. It survives refresh/restarts with the upload. Review shows
its lesson assignments and warns that publication creates the course and enables
Office Hours. The exact pending course definition is included in the approval
fingerprint. Publication merges it under the existing shared lock and journal,
rejects conflicting course names/lesson IDs, and preserves unrelated configuration.
Retries reuse the same IDs and cannot duplicate the course. No course configuration
is written to runtime S3 until the instructor approves publication.
